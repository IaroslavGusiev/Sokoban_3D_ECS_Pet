# Sokoban architecture

Current design, checked against source on 2026-10-27. This document describes implemented behavior and ownership. Start with [setup](SETUP.md) to run or author content. Completed milestones and their test results are [historical records](history/README.md), not current setup instructions.

## Purpose and boundaries

This pet project exercises deterministic DefaultEcs rules and explicit OOP ownership around asynchronous Unity presentation. Gameplay includes moves, pushing, walls, win detection, a level countdown with automatic restart on timeout, automatic level progression, R restart, Z undo during Playing, K player-skin cycling, and temporary N level cycling in Editor/development builds. Skin selection and all skin components live in presentation; switching skins does not mutate gameplay state.

| Folder under Sokoban/Assets/_Sokoban/Code | Assembly | Namespace | Responsibility |
| --- | --- | --- | --- |
| Core | Sokoban.Core | Sokoban.Core | Commands/components, parsing/population, movement, Simulation and Core pipeline. |
| Unity | Sokoban.Unity | Sokoban.Presentation | Composition, input/controller, text loading, shared prefab cache, per-run binding and projection. |
| Editor | Sokoban.Editor | Sokoban.Editor | Addressable string-address validation; excluded from players. |

Unity is 6000.0.63f1, DefaultEcs 0.17.2, Zenject 9.2.0, Addressables 4.1.1, and UniTask 2.5.11 from the existing Assets/Plugins installation. PrimeTween 1.5.1 is already installed from Packages/com.kyrylokuzyk.primetween.tgz through the existing local-tarball UPM entry; this refactor reuses that dependency. Core has noEngineReferences/overrideReferences enabled; its compiled references remain netstandard and DefaultEcs only.

Editor address validation and its tests live in the Editor-only Sokoban.Editor and Sokoban.Editor.Tests assemblies. [ASSEMBLIES.md](ASSEMBLIES.md) inventories all 22 source/vendored asmdefs and the resolved-package snapshot. Core friends only Sokoban.EditModeTests (internal movement systems and solver observation) and Sokoban.App.EditModeTests (internal Simulation composition seam/MovementSystem). The unused Sokoban.PlayModeTests entry was removed. Sokoban.Core.Tests uses public Core APIs, has no Unity references, and its source namespace is Sokoban.CoreTests.

## Deterministic Core

GridPosition is an immutable integer X/Y value. PlayerTag, BoxTag, WallTag, GoalTag, and FloorTag are readonly structs. Simulation.Send accepts cardinal MoveCommand values and preserves the first pending MoveRequest.

Simulation owns a new World and receives a concrete SimulationPipelineFactory. SimulationPipelineFactory.Create(World) constructs and returns an owned SystemPipeline with fresh systems in this order: UndoSystem, MovementSystem (validation then application), MoveCountSystem, GoalTrackingSystem, WinCheckSystem, then LevelTimerSystem. Its CreateSystems iterator supplies these actual systems lazily to SystemPipeline; no feature factory objects are created. Simulation owns, ticks, and disposes the returned pipeline. WinCheckSystem iterates goal and box entity sets directly without per-tick collections or LINQ, and sets LevelCompletedTag on the dedicated level-state entity once every goal is occupied by a box. Simulation.IsCompleted exposes that tag. Completion is latched; Simulation.Send rejects commands after completion or timeout. Construction failures release acquired resources before propagating; normal disposal releases systems before the world. Cleanup exceptions propagate, without aggregation or idempotence flags.

Simulation retains explicit private _player and _levelState references in its owned World. After LevelPopulator creates the board and player, Simulation creates exactly one nonvisual entity with LevelStateTag, LevelTimer, MoveCount, and a run-owned MoveHistory. This entity has no GridPosition, view-kind tag, or presentation adapter; the existing view query excludes it. PlayerTag, GridPosition, movement requests/plans, and player-specific presentation components remain on the player. Both entities end with the Simulation world. LevelTimer carries RemainingSeconds on the level entity. The public Simulation constructor rejects nonfinite or nonpositive time limits with ArgumentOutOfRangeException before creating its World. Every attempt starts with the supplied finite positive budget. LevelTimerSystem queries LevelStateTag/LevelTimer entities without LevelCompletedTag or LevelTimedOutTag. It returns without writing on zero delta; otherwise it subtracts the supplied delta, clamps at zero, removes pending MoveRequest/MovementPlan from its captured player at expiration, and adds LevelTimedOutTag. Win runs first, so a winning move on the final tick succeeds and leaves the timer at its value before that tick. The timer then stays frozen through query exclusion. Simulation.Tick rejects nonfinite or negative deltaTime with ArgumentOutOfRangeException before running any system, leaving pending movement, positions, count, and timer unchanged; zero delta is accepted and can process a queued move. Valid calls tick the pipeline; terminal rules live in Core systems and Send. Simulation reads IsCompleted, IsTimedOut, RemainingSeconds, and Result from _levelState and sends movement requests only to _player; LevelRun forwards Result and the controller exposes status through IGameplayStatus. Time is synchronous input to Core; no Unity clock, async delay, or wall clock enters the rules.

The level entity holds readonly MoveCount with only Value. MoveCountSystem captures the single tagged player and its starting GridPosition during construction, retaining the previous-position snapshot privately for that run. It queries LevelStateTag/MoveCount, runs directly after movement, compares the player position with the private snapshot, and increments the level count at most once per tick. On an undo tick, UndoProcessedTag makes the count system synchronize its private position snapshot and consume the tag without incrementing the restored count. Blocked moves and pushes leave it unchanged; the count includes the winning move before WinCheckSystem latches completion. Simulation.Result is a readonly LevelResult with Moves, ElapsedSeconds, and RemainingSeconds. ElapsedSeconds is the original time limit minus the current timer, so completion preserves the existing freeze-before-winning-tick-decrement behavior.
LevelPopulator is a public, sealed, stateless Core instance. Its Populate(World, LevelDefinition) method creates the player, walls, and boxes as separate entities. It also creates exactly Width * Height floor entities covering every cell, including cells underneath walls. Each floor has GridPosition and FloorTag; goal positions additionally have GoalTag on that same floor entity. There are no separate goal entities. LevelPopulator still creates 76, 78, and 98 board entities/views for the three shipped levels. Simulation adds one nonvisual level-state entity, making total Core counts 77, 79, and 99; expected view counts remain 76, 78, and 98. Simulation requires the populator through its constructor and still creates, owns, and disposes its world; the populator retains no world or run state and has no Zenject dependency.

MovementValidationSystem consumes requests, rejects blocked/invalid moves, and creates a MovementPlan. Walks and pushes share one destination calculation at the planning boundary: coordinates are added using long intermediates, and destinations outside the Int32 range reject the entire move without wrapping, changing positions, or counting a move. LevelDefinition permits authored integer positions without a dimension-based coordinate-range check; parsed levels remain enclosed by their walls. GridPosition construction and its raw addition operator remain unchanged; the rejection contract belongs to movement planning. A push stores box then player steps with expected source positions. ApplyMovementSystem preflights every participant, consumes the plan, and writes positions through entity.Set. Destroyed, disabled, moved, foreign-world, or missing participants reject the plan before writes.

DefaultEcs notifications are synchronous: an observer can see the box position change before the player's change. Observers must not mutate participants, re-enter movement, or throw during commit; there is no rollback for arbitrary observer exceptions. Runtime movement has no explicit board-bounds check; text parsing validates playable-area enclosure.

SystemPipeline accepts an IEnumerable<ISystem<float>>, takes ownership incrementally while enumerating it, and owns a SequentialSystem for ordered execution and reverse disposal. SimulationPipelineFactory and ViewPipelineFactory declare their systems with yield return new so that a later constructor failure occurs inside pipeline acquisition, where already acquired systems can be released in reverse. Both factories are concrete, sealed, non-static, stateless classes: they retain no World, ViewContext, systems, or run state and only construct pipelines. There is no World argument on SystemPipeline, IFeature, feature registry, factory interface, or per-system factory wrapper. The internal Simulation constructor accepts a Func<World, SystemPipeline> for isolated composition/lifecycle tests; production passes SimulationPipelineFactory.Create. SimulationReplay constructs the same Core factory directly and passes its Create method with recording explicitly disabled. Core has no Unity or Zenject dependency or injection attributes. The production order remains explicit, with fresh systems for every run/world. SequentialSystem checks its own IsEnabled; MovementSystem and the presentation composites delegate IsEnabled, Update, and Dispose to their owned sequences. Child rule systems retain their interface properties without local enable guards. Exactly one stable PlayerTag entity is supported per Simulation; LevelPopulator creates it, and normal Core systems preserve its identity. Public World access supports inspection and composition, not arbitrary multi-player worlds or player creation, destruction, or retagging during a run. Internal movement systems assume this invariant rather than validating malformed player counts each tick. The level-state entity remains singular and nonvisual.

MovementSystem is an internal ISystem<float> composite with an owned SequentialSystem running MovementValidationSystem then ApplyMovementSystem. It gates both stages through IsEnabled and releases acquired children if a later construction fails. Each supported movement tick invokes validation once, immediately followed by application once. MovementPlan is transient output of that uninterrupted pair, consumed by application before writes; a completed movement tick leaves no plan. Repeated validation without application, skipped/reordered stages, mid-stage owner disabling/topology changes, and individual child-system disabling are unsupported. Pause/resume the whole pair between ticks: requests remain pending without partially validated plans, then run once on resume. An interrupted partial tick has no recovery guarantee; callers must not depend on a later validation pass cleaning it up. Application preflight remains defensive and is tested independently for atomic push rejection.

## Undo within one attempt

Simulation.CanUndo reports available history while the attempt is neither completed nor timed out. Simulation.RequestUndo returns whether an UndoRequest was accepted onto the level-state entity. Repeated requests coalesce into that one component; an empty or terminal attempt rejects them. Invalid numeric ticks leave an accepted request and all state untouched. Send rejects forward commands while an undo is pending, and UndoSystem also clears any already-pending player MoveRequest/MovementPlan before processing it, so forward movement and undo are mutually exclusive within a tick.

ApplyMovementSystem records a CommittedMove only after successful preflight and all participant writes. Each record reuses the one- or two-step MovementPlan (entity, before position, after position) and stores the previous level move count. MoveHistory contains a stack of these records on the level-state entity; there is no board snapshot, redo stack, persistent ID, or global history service. Rejected/blocked/overflow moves add no record. Simulation clears the stack before disposing its World, including when pipeline disposal throws; replacement runs start empty.

UndoSystem preflights every recorded participant against the current World, liveness, enabled GridPosition, and expected after-position. It also checks every reverse destination for walls or boxes outside the participants that will move together. Only after the entire preflight succeeds does it restore positions through entity.Set, restore MoveCount and pop the record. Every consumed request sets UndoProcessedTag, including rejected reverse preflight, to suppress forward counting that tick. Failure consumes the request but retains the record and performs no position/count writes. The existing observer restrictions and lack of rollback for arbitrary observer exceptions apply to both forward and reverse commits.

UndoProcessedTag synchronizes MoveCountSystem's private player snapshot without incrementing. UndoSystem also synchronizes affected BoxGoalState snapshots before GoalTrackingSystem runs, so returning to an old goal publishes no BoxEnteredGoal message or new bump. A later forward arrival still publishes normally. Win/countdown ordering remains unchanged; undo does not restore elapsed time or timer values, and the countdown consumes the full undo tick. Completed/Finished attempts cannot be undone.

GameplayController.CanUndo additionally requires Playing, ready views, and no ViewMove interpolation. The overlay and Z shortcut use the same controller path, sampled before phase processing; requests made while unavailable are dropped rather than saved until binding/motion finishes. Restart/next-level commands retain priority over undo, and automatic timeout/progression command suppression remains intact. Accepted undo clears LevelRun's buffered forward command before the normal simulation/presentation tick, and skips reading forward movement that tick. All UI requests only queue an action.

Reverse position notifications reuse ActorMotionSystem and the existing player animation/interpolation. Moving a box interrupts/restores its existing goal feedback through the current lifecycle system. Undo retains the Simulation, entities, view GameObjects, and cached assets, and creates no additional view-provider or Addressables requests. There is no undo after victory, redo, persistence, or cross-run history.

## Recording and replay

Every Simulation created through its public constructor records supported gameplay API inputs from the beginning of that run. The ordered SimulationInput stream contains every Send(command) and RequestUndo() attempt, including invalid commands, logically rejected requests, and coalesced duplicates. No acceptance result is substituted for a request: replay invokes the same API and lets current Core rules reproduce its outcome. ExportRecording and CaptureSnapshot are observations, not gameplay inputs.

Tick appends its input only after the pipeline returns successfully. Every successful idle, zero-delta, and terminal-state tick is retained with the exact supplied float value, including its bit pattern; no fixed step, wall clock, or resampling is introduced. Existing time-limit/delta validation remains at Simulation entry points. Invalid duration construction produces no run; invalid ticks neither mutate gameplay nor enter the stream, and pending requests remain intact. Subscriber-driven API reentry, arbitrary observer exceptions/partial ticks, and direct external World mutation remain outside the recording contract. Presentation transforms and skin components are not replay inputs or comparison data.

Simulation owns the mutable input buffer and retains its immutable initial LevelDefinition. ExportRecording copies the level data and inputs into a sealed SimulationRecording with read-only collections, initial time limit, and immutable value inputs. The export contains no DefaultEcs entity handles, Unity objects, async types, or live buffers. Continuing the source cannot change an earlier export, and exported recordings remain usable after source disposal. Dispose clears the run's input buffer; export must happen before disposal. ExportRecording throws InvalidOperationException on a disposed or recording-disabled Simulation.

Exports may end between ticks. Trailing movement/undo requests are replayed in order and remain pending at the endpoint; there is no implicit flush tick. The endpoint snapshot intentionally describes visible gameplay state, not pending components or private history. Tests continue both source and replay with another tick to verify pending work and reconstructed history agree.

SimulationReplay owns a fresh Simulation/World constructed from the exported level and time limit. Step executes exactly one recorded input; Run executes the remainder. Both use real Send, RequestUndo, and Tick calls, rebuilding undo history through normal successful movement rather than assigning positions. Its borrowed Simulation property supports snapshot inspection and explicit Core continuation while the replay owner is alive. Use a using scope for the replay. Step failure disposes the owned Simulation before propagating; Dispose clears ownership and is safe when a using scope cleans up after that failure. Simulation constructor failure retains its normal World cleanup. Completed Step/Run calls add no extra tick.

Replay and internal custom-pipeline fixtures use the internal Simulation constructor with recording disabled by default; only the normal public constructor enables it automatically. Thus replay never recursively records itself, and recording export from its Simulation is unavailable. Multiple replay owners share only immutable export data and never the World, entity identities, undo history, or the source's live run.

CaptureSnapshot returns an immutable GameplaySnapshot: player position, copied box positions sorted by X then Y, move count, remaining/elapsed time, completion, timeout, undo availability, and board revision. Value equality and hashing compare those fields exactly; entity IDs, entity/query order, transforms, skins, pending request components, and history records are excluded. Replay reconstructs the revision through the normal rules. This milestone verifies identical Core execution with identical input sequences, deltas, rule version, and runtime; it does not promise cross-platform floating-point equivalence. No JSON/file persistence, network transport, playback UI, seeking, rewind, speed control, fixed-point arithmetic, or timestep redesign is provided.

## Asynchronous hints

The level-state entity also holds BoardRevision, starting at zero per Simulation. ApplyMovementSystem increments it after a successful full forward commit; UndoSystem increments it after a successful reverse commit. Undo restores positions/count but never an earlier revision. Blocked/rejected moves, failed undo, idle ticks, timer updates, and skin changes leave it unchanged. Simulation exposes the revision synchronously; it remains Unity-independent and creates no additional entity or view.

HintSolver is a stateless pure C# breadth-first search over player position and canonical box positions ordered by X then Y. Its FIFO loop visits Successors in Up, Down, Left, Right order; TrySuccessor handles walks and delegates box movement to TryPush. Walking reuses immutable search-state arrays; pushing copies and reorders them. State equality compares player/boxes and excludes FirstMove path metadata. Budget checks still occur after duplicate rejection and before admitting a successor, including a winning successor; the initial state counts toward the budget. TryStep retains long arithmetic and rectangular bounds/wall checks. Outcomes remain Found with a shortest-move recommendation, NoSolution, BudgetExhausted, or AlreadySolved. Cancellation is checked per dequeued state and attempted direction. The internal expansion-observation overload and deterministic mid-search cancellation test are unchanged. LevelRun captures an immutable LevelDefinition on the main thread; no worker reads a live World, entity, view, or Unity object. The independent test-only solver remains a separate oracle.

IHintService/HintService remain the background execution boundary, running HintSolver on Task.Run with a 100,000-state budget. ServicesInstaller binds a concrete HintCoordinator as self only; it is neither an independently scheduled ITickable nor a Zenject IDisposable registration. GameplayController is its sole disposal owner and preserves IGameplayCommands/IGameplayStatus by delegation. The coordinator owns the queued request, captured run/revision, active HintOperation, status/direction, cancellation/invalidation, completion polling, and display decisions. It accepts requests only during Playing with ready, stationary views and no queued/active operation. The controller consumes the request at the same beginning-of-tick point as other UI requests, starts eligible work before skin/gameplay ticks when restart/next-level commands do not take priority, sends non-Playing/release notifications before disposing a run, and polls after gameplay ticks and commands. Main-thread capture and application therefore retain their original ordering. Hints neither execute a move nor pause the countdown.

HintOperation (renamed from HintCalculation with its asset GUID preserved) owns search cancellation and observes success, cancellation, and failure into Task completion data. On a current Found result needing a visual, the coordinator starts its separate arrow observation through IViewProvider. Each phase has an explicitly owned cancellation source; cancellation and source disposal synchronize, and each observer disposes its source in finally after it finishes. Both observers are static and retain only the copied board/service or shared provider plus cancellation ownership and completion data, never a coordinator, controller, run, World, entity, or instantiated view. They do not create/display Unity objects or apply gameplay state. Invalidation cancels both phases and drops the operation identity. Cancellation-ignoring late successes/failures remain observed as data and cannot apply to old/new state. Polling checks IsCompleted before retrieving completion data, with no blocking wait or new fire-and-forget task. Current search failures log once; ViewAssets retains asset-failure logging, retry, and release ownership.

Both search and arrow completion require the same active operation identity, captured LevelRun, unchanged BoardRevision, Playing phase, and ready, stationary views before application. Successful movement/undo, restart/replacement, completion, timeout, disposal, or unavailable views invalidate pending/displayed hints, cancel pending display, and hide an existing arrow. Returning to identical positions through undo does not restore validity because revision increased. A synchronous skin change can preserve a hint; a pending rebind invalidates it. Idle/blocked movement and timer changes preserve it. HintStatus stays Calculating and CanHint stays false while the required arrow asset is loading; only valid main-thread display changes it to Available and publishes HintMove. Load failure reports Failed while gameplay remains Playing and another request is available; ViewAssets retries a failed cached handle in a later frame.

HintArrow is appended as presentation-only ViewKind value 5, preserving Floor through Goal values 0 through 4. Its Default catalog entry resolves views/hint_arrow, registered in the existing local Addressables group. Assets/_Sokoban/Prefabs/HintArrow.prefab retains GUID 5632dd1764ea72b4fb8ab716111941ce, appearance, mesh, and material. ServicesInstaller and LevelRunFactory/LevelRun/ViewLayer no longer carry a serialized or constructor prefab reference. The coordinator loads through shared IViewProvider/ViewAssets using the existing Addressables abstraction; canceling one caller never releases the cached handle. After identity/eligibility checks, ViewLayer validates the HintArrow facade and lazily creates one instance beneath its owned root. Later requests reuse that instance without another load. The arrow has no collider, entity, or adapter and retains its grid direction/offset mapping. Run disposal disables/destroys the root before simulation disposal; GameplayLifetime disposes controller/coordinator/runs before the shared view cache and config assets. Editor address validation checks the Default arrow entry's unique included GameObject address and required HintArrow facade. Built-content verification requires rebuilding Addressables after catalog/registration changes.

## Parsing and tests

LevelParser accepts #, -, @, $, ., *, and +. Text starts at the highest y coordinate; Up is +y. CRLF is normalized, trailing empty rows ignored, and row characters preserved. Diagnostics identify invalid symbols/rows and begin with line N: or level:. Validation checks rectangular rows, one player, at least one box, equal box/goal counts, and a four-direction flood fill enclosed by walls. Boxes/goals are passable for enclosure; unreachable edge cells, including diagonal-only adjacency, are valid.

After checking box/goal counts, LevelParser rejects an already solved level with "level: the level is already solved; leave at least one box off its goal." The three shipped levels still parse and solve. LevelDefinition validates positive dimensions and nonnull collections at its public boundary. No Unity or async types enter the model.

Core.Tests discovers every Assets/Levels/*.txt. The independent BFS LevelSolver returns the shortest move sequence plus the player's predicted GridPosition after each move, with a 2,000,000-state cap. Replay sends each move through a real Simulation and asserts each player position and final box/goal positions. The shipped solutions remain 6, 12, and 11 moves. This independent oracle stays test-only; runtime hints use the separate HintSolver and are checked against it.

ViewAssets implements IViewProvider and IDisposable. IViewProvider.LoadAsync takes ViewKey and CancellationToken. ViewKey is an immutable equatable Kind/Skin pair; SkinId contains Default (Doctor), Alternate (Farmer), and Punk. The provider resolves the catalog entry first and keys its cache by that entry's pair, so absent alternate skins reuse the same Default handle. Its constructor retains IStaticDataProvider without loading anything; LoadAsync reads the loaded ViewCatalog through GetViewCatalog. Cache misses start one IAddressablesService.Load<GameObject>; concurrent callers for the same resolved pair reuse the pending/successful handle. Each caller uses IAddressablesService.AwaitAsync with its cancellation token; the service observes cancellation immediately and never automatically releases the shared handle. Cancellation stops the caller's wait; the shared handle remains owned by the provider. Cancelling a caller never cancels or releases the shared handle. Successful prefabs stay cached across K, R, and N. CachedLoad.OnCompleted records Time.frameCount on failure, including immediate failure at creation. Requests in that frame share the failed handle and exception. A request in a later frame removes the failed cache entry and releases its still-valid handle before starting a fresh load. This prevents synchronous invalid-key failures from creating one failed handle/log per entity in a binding tick.

Failures log once per load attempt, covering synchronous catalogue/setup/conversion failures and asynchronous operation failure. A CachedLoad entry deduplicates its completion-callback log and its callers' exception-path logs, even if all callers stopped waiting. Cancellation is propagated without an error log. Each affected entity is separately marked ViewFailed; the binding operation does not duplicate provider logs. A later request can retry and can produce a new failure log. Current entities with ViewFailed do not retry automatically; a skin request clears their failure marker, while R or N builds a fresh run. A stale request's result or failure cannot bind or mark failure for a different desired ViewKey. Exceptions from instantiation/adapter installation remain logged by their binding operation.

Release while loading uses immediate owner release, without awaiting underlying completion. Addressables' internal execution reference survives until completion and final destruction. Addressables 4.1.1 also invalidates outstanding handles during ExitingPlayMode, potentially before Zenject's OnDestroy disposal. The approved IsValid checks remain at provider disposal and temporary text cleanup to skip already-invalidated handles.

## ECS presentation flow

### Addressables access

IAddressablesService exposes typed Load(address), LoadByLabel(label), AwaitAsync(handle, token), and Release(handle). ServicesInstaller binds one stateless AddressablesService. It is the only runtime class that calls Addressables loading/release APIs or converts handles to UniTask. It adds no cache and owns no handles. AddressableLevelSource, StaticDataProvider, and ViewAssets receive it through constructor injection and retain their respective temporary, scene-config, and prefab-cache ownership policies.

AwaitAsync observes cancellation immediately and disables automatic handle release. Cancelling one waiter does not release an asset or cancel the underlying shared operation; the owner still releases its acquired reference exactly once. Release checks handle validity to tolerate Addressables invalidation on Play Mode exit. It does not make releasing the same live reference twice safe, because another owner can keep the shared operation valid. Config retry/validation, view failure logging and retry, and level parsing remain with their current owners.

### Static config loading

The assets in Assets/Addressables/Config are GameplaySettings.asset, LevelList.asset, and LevelViewCatalog.asset. Their stored settings use field-targeted SerializeField auto-properties with public getters and private setters. GameplaySettings exposes timer, completion-delay, and movement float properties; LevelList.Levels is a serialized array; ViewCatalog.Entries and KindEntry.Skins are lists. Config classes contain no Validate methods or FormerlySerializedAs attributes. Values are authored and saved through the Unity Editor using the current serialized backing-field names; existing values were saved through Editor APIs before removing migration support. They retain their GUIDs after moving out of Resources. StaticDataProvider.LoadAsync uses IAddressablesService.LoadByLabel<ScriptableObject> and AwaitAsync to load the Configs label, requires exactly one of each expected type, and publishes the resulting config set. All three configs are trusted authored data without runtime Validate calls. This authoring policy is separate from the public Simulation numeric contract: Simulation checks its own time-limit and delta arguments; config-level validation is not reintroduced. GetGameplaySettings, GetViewCatalog, GetLevelConfig(index), and LevelCount are synchronous reads after loading. A read before readiness fails loudly; there is no Resources fallback or default config creation. Consumers retain the provider during construction and access configs during the owned startup/load flow. GameplayController.RemainingSeconds requires completed config loading when no run exists.

Pending callers share one preserved initialization task. The caller starting that attempt controls its cancellation; a later waiter's cancellation only ends its own wait. Provider disposal also cancels the attempt. Failed, missing/duplicate-type, or cancelled attempts release their owned batch and clear it for retry. Completed configs stay cached for the scene lifetime. A captured attempt identity prevents cancellation/disposal cleanup from releasing another attempt, and a token check after awaiting prevents late completion from publishing cancelled data. Addressables handle IsValid checks cover Editor play-mode invalidation. Config handles remain separate from ViewAssets prefab handles and AddressableLevelSource temporary text handles.

Editor address validation additionally requires one labeled asset per config type and checks group/catalog label inclusion. The runtime label load requires the expected config types in actual built content; changing saved assets or label assignments still requires rebuilding Addressables for Use Existing Build.

### Entity and view lifetime contract

Presentation supports creating, disposing, and recreating eligible viewable entities while the same World and ViewLayer remain alive. A new entity with GridPosition and a supported view-kind tag enters the normal binding query and receives its view on presentation ticks. Its kind-selection tags and GridPosition component presence remain stable for that entity lifetime; movement may change position values. This is presentation ownership support, not a change to Simulation's single stable player, movement/undo history, or static level/hint topology contracts. Controlled tests use floor entities and do not add dynamic players or boxes to normal gameplay.

ViewBindingSystem owns a Dictionary<Entity, ViewOwnership>. DefaultEcs 0.17.2 Entity equality includes world, slot, and generation, so reuse of storage cannot transfer ownership. A live entity also holds the same internal presentation-only ViewOwnership reference, allowing SkinSwitchSystem to release its bound view through the same owner. Each record retains its original entity identity, current ViewLoadOperation identity, and optional instantiated GameObject. The registry survives ECS entity disposal and does not rely on reading removed components to clean up a view.

Every enabled binding update sweeps tracked ownership, even when no entities need binding. Removal invalidates/cancels that entity's waiter and deactivates its bound view by the next normal presentation tick. GameObject destruction uses Unity's deferred Destroy; OnDisable cleanup stops view-owned animation/feedback during that tick, with destruction finishing at the frame boundary. If the entity is still alive (skin replacement or run disposal), cleanup calls EntityView.Uninstall and removes the owned transform. If it is dead, cleanup skips adapter Uninstall and all entity component access: ECS already removed those components, and the GameObject's OnDisable/OnDestroy hooks own Unity-only resource cleanup. Adapters must keep such cleanup independent of ECS. The view reference is cleared before callbacks/destruction, so later run disposal does not repeat that ownership release. Destroying an instance never releases a shared prefab handle.

Presentation exclusively owns ViewOwnership, ViewPending, ViewFailed, ViewSkin, SkinChangeRequest, TransformComponent, and instantiated views. Entity disabling/re-enabling, retagging, external removal/replacement of presentation components, external destruction of bound views, and arbitrary adapter-driven entity mutation during binding remain outside this contract. Partial adapter-installation failures retain their existing failure/partial-write behavior until explicit skin/run cleanup; this task adds no transactional adapter installation. Ready remains based on readiness components, not arbitrary Unity-object health.

ViewLayer still cancels the run token and disables/destroys the root before disposing its pipeline; Simulation disposes its World afterward. Binding disposal cancels all owned waiters, releases remaining live views/adapters, removes its live ownership/pending components, clears tracking buffers, and disposes its candidate query. No additional lifetime subscription or scheduler is introduced. Existing whole-run cancellation and systems-before-world cleanup remain required.

### Binding and projection

Every visual now follows one path:

needs view -> ViewPending -> TransformComponent, or ViewFailed.

ViewKeyMap prioritizes WallTag, BoxTag, PlayerTag, GoalTag, FloorTag exactly as before, and reads the desired skin from ViewSkin, defaulting to Default when absent. Goal floors therefore select the Goal prefab.

ViewBindingSystem implements ISystem<float> and owns its candidate EntitySet. ViewQuery.Viewable retains the common GridPosition plus supported-kind predicate; binding still excludes ViewPending, ViewFailed, and TransformComponent. An explicit update is necessary because DefaultEcs 0.17.2 AEntitySetSystem skips PreUpdate/PostUpdate when its set is empty, which would miss removal of the last bound entity or completion of a pending request. Each update snapshots tracked records for removal cleanup, buffers eligible candidates before component writes, starts fresh requests with ViewPending, and polls previously pending completions. Immediately completed provider results may bind in that same tick. No asynchronous continuation applies presentation state.

ViewLoadOperation captures only the provider, requested ViewKey, and its cancellation ownership. Its static observer returns prefab/error/cancellation completion data, never retaining an entity, World, owner registry, view root, or instantiated view. Each caller has a cancellation source linked to the run token. Entity removal cancels its waiter without releasing or canceling the shared ViewAssets cached load. An observer disposes its source in finally when observation finishes; cancellation-ignoring providers can finish or fail later, but their outcome remains observed without reattaching ownership. Cache coalescing, failure logging/retry, and handle release remain owned by the unchanged ViewAssets and Addressables abstraction.

Only the owned main-thread binding update applies results after checking run cancellation, original World/entity liveness and generation, the entity's ownership-record reference, active request identity, and the requested versus desired ViewKey. Removed/recreated entities and old operations cannot bind, mark failure, or clear a newer request. A stale-key result clears only its own ViewPending, permitting the desired skin request on the next tick. Existing pending skin changes still wait for the current observation to finish; they do not start parallel requests for that same live entity. Other entities and removed/recreated generations may have overlapping observations. Current provider failure sets ViewFailed and clears pending without automatic per-entity retry; skin requests and run replacement retain recovery. A current cancellation clears its pending request. Provider-side failures retain ViewAssets logging; instantiation/adapter failures retain the binding exception log.

For a valid success, binding reads the latest GridPosition/ViewMove, preserves authored rotation or the player's established ActorViewState facing, instantiates under ViewContext.Root, and names the instance Key (x, y). EntityView installs adapters before the binder writes the authoritative TransformComponent. EntityView remains optional. EntityAdapter retains Install/Uninstall; ComponentAdapter<T> installs through Set and uninstalls through Remove<T>. TransformAdapter, PlayerAnimatorAdapter, and BoxGoalFeedbackAdapter retain their existing contracts and serialized identities. Normal skin changes and live run cleanup uninstall adapters; dead-entity cleanup deliberately uses Unity-only disable/destruction hooks instead.

ViewLayer creates its ViewContext and calls its explicitly supplied ViewPipelineFactory.Create(World, ViewContext). The factory returns an owned SystemPipeline with fresh presentation systems in this order: SkinSwitchSystem, ViewBindingSystem, ActorMotionSystem, GridTransformSyncSystem, PlayerAnimationSystem, then BoxGoalFeedbackCompositeSystem. Its private CreateSystems iterator supplies these lazily to SystemPipeline. ViewLayer owns, ticks, and disposes the returned pipeline. No feature object passes through LevelRunFactory or LevelRun. FeaturesInstaller and the feature wrappers were removed; the saved GameplayScene's SceneContext list and components now contain only ServicesInstaller and GameplayInstaller. The buffered SkinSwitchSystem consumes SkinChangeRequest, releases a tracked bound view through ViewOwnership (retaining its previous fallback for manually bound transforms), writes ViewSkin, clears ViewFailed, and consumes the request. Existing ViewPending remains until its awaited operation completes or the run is cancelled. GridTransformSyncSystem projects every bound entity into Unity world space (X, 0, Y), including floor cells. Destroyed Unity transforms are skipped using Unity null semantics. Projection never writes gameplay positions back. Player and box views interpolate during ViewMove; other views project immediately. Player rotation follows its last successful move.

ViewLayer creates its own root, token source, context, two readiness EntitySets, a player query, and a ViewMove query, and acquires its pipeline from ViewPipelineFactory. The missing-view set uses ViewQuery.Viewable without TransformComponent; the failed-view set contains every entity with ViewFailed. Status is Failed if the failed set is nonempty, Binding if the missing set is nonempty, otherwise Ready. This includes unrequested viewable entities and gives failure priority even when a transform is present. No readiness system or stored aggregate ECS marker is needed.

ViewLayer owns a player query, writes the initial ViewSkin directly before the first tick, and SetPlayerSkin writes one SkinChangeRequest to every player. Dispose cancels before any world can be disposed, disables/destroys the root, disposes the pipeline and all four query sets, then disposes the token source. A late result returns without touching the old entity; Constructor failure releases acquired resources and rethrows.

## Player animation and visual movement

Core still commits complete moves and pushes synchronously. ActorMotionSystem remains the public ISystem<float> facade with constructor (World world, float duration). It owns one SequentialSystem in the exact order ActorStateInitSystem, ActorMoveDetectionSystem, then ViewMoveAdvanceSystem. IsEnabled, Update, and Dispose delegate to that sequence. Disabled updates skip all three children. Construction tracks acquired children and disposes them in reverse if a later acquisition fails; the detection system also releases its acquired player/box queries and base set on construction failure. Normal disposal releases queries, leaving entity/component and World lifetime with their existing owners.

ActorQuery.Actors centralizes the GridPosition plus PlayerTag-or-BoxTag predicate beside ViewQuery. The internal child systems extend it with their own component conditions. ActorStateInitSystem uses buffered AEntitySetSystem iteration over actors without ActorViewState, replacing the manual CopyTo/Array.Resize buffer. It initializes from the current GridPosition, with identity Facing and HasFacing false; it neither starts motion nor changes a Unity transform or authored facing. Lazy actors initialize before detection in the same composite update. ActorMoveDetectionSystem owns separate player and box queries with ActorViewState. Its PreUpdate calculates successful-push information once before any detection entity writes; the installed DefaultEcs 0.17.2 hook runs before buffered iteration. A player entering the previous cell of a box that moved by the same delta is a successful push. Both delta calculations use long arithmetic so Int32 wrapping cannot produce a false push. Detection then compares each actor snapshot with GridPosition, creates/retargets ViewMove, and updates facing/position data. Rejected requests do not change positions, start visual motion, or turn the player. No Unity reference or animation component was added to Core.

A changed actor receives readonly ViewMove (From, To, Elapsed, Duration, IsPushing). Its pure Advance(deltaTime) returns a new value, using the existing upper clamp on elapsed time; IsDone and Position describe that value without Unity-object side effects. There is no new duration/delta validation. ViewMoveAdvanceSystem uses buffered AEntitySetSystem iteration over actors with ViewMove, after all detection completes. It advances existing and newly detected moves with the same supplied delta, removes completed components, and otherwise replaces them through entity.Set. Thus new moves advance in the same composite update, including synchronized player/box steps. GridTransformSyncSystem interpolates the transform until completion, then projects the exact destination after ViewMove removal. ActorViewState.HasFacing becomes true on the first detected movement. Until then, binding and projection preserve the prefab rotation. Afterward, ActorViewState preserves the player's facing across skin replacement. GridTransformSyncSystem writes position and rotation only when they differ from their targets. Retargeting starts from the previous ViewMove's current position before advancement of the new step; ordinary application input is buffered instead. A new run initializes without movement. Skin replacement keeps existing motion/facing and binds the new view at the current visual position. It does not restart the step or retain the previous Animator reference.

LevelRun retains at most one pending cardinal command; the first is preserved and further commands are dropped until it is submitted. On a Playing tick, it submits that command only when ViewLayer has no ViewMove, then ticks simulation and presentation. A step finishing in this tick permits submission on the next Playing tick. Core and the countdown continue ticking while input waits for visual movement. Commands cannot survive run replacement. Presentation motion still advances during view-failure recovery and completion; Loading skips it along with all presentation work.

That presentation component references the PlayerAnimator MonoBehaviour facade, which wraps the nested Unity Animator. PlayerAnimationSystem queries the component and drives Moving plus the Push layer weight from ViewMove. Push weight blends over 0.05 seconds. Adapter uninstall removes the component before skin view destruction.

Original model prefabs and the legacy cube player prefabs remain available; only the three wrappers are registered as player addresses.

## Controller and composition

GameplayController is the sole Zenject IInitializable/ITickable driver. Public Tick() delegates to internal Tick(deltaTime), which runs the full orchestration and supplies a deterministic seam for friend tests. GameplayLifetime owns its disposal along with ViewAssets and StaticDataProvider. The controller's only run field is a private LevelRun. LevelRun is internal, retains private Simulation/ViewLayer fields, forwards movement and completion/readiness queries, and ticks simulation before presentation. Simulation and ViewLayer each implement IDisposable directly. LevelRun calls their concrete Tick methods and owns their ordering; there is no shared layer interface or layer list.

The controller's _playerSkin survives restarts and level changes. Every new LevelRun receives it and forwards it to ViewLayer before initial binding. In a non-Loading tick with a run, HandleSkinInput uses SkinCycle.Next and sends SetPlayerSkin before layer ticking. SkinCycle caches Enum.GetValues and wraps over contiguous SkinId values 0..n-1, so adding a third enum value needs no controller change. KeyboardMoveInput maps this to K, with the existing required-keyboard contract. Readiness is re-evaluated in BindingViews and ViewsFailed. Playing ignores Binding status but transitions to ViewsFailed on Failed status after ticking the run. Subsequent simulation ticking and movement input pause while presentation keeps ticking; K can clear the failure and recover through BindingViews to Playing without R.

The controller keeps an enum-based state machine with Loading, BindingViews, Playing, Completed, ViewsFailed, LevelFailed, and Finished. All state changes go through TransitionTo(GameplayPhase next); entering Completed resets the completion-delay timer and appends the current run's LevelResult once. State handlers remain private controller methods. Initialize asynchronously loads the Configs batch, requires its expected config types, and then loads definition 0. Every definition-load attempt first awaits StaticDataProvider.LoadAsync, which returns immediately after a successful config load. R after config failure therefore retries the config stage before the attempted level. Loading returns before input, layer ticking, or command handling. In every other state an existing run ticks presentation; only Playing reads/sends movement input and ticks simulation. A queued Core request therefore remains pending while a replacement definition loads. The attempted index is stored before awaiting, so LevelFailed + R retries that index even if N failed before producing a definition. ViewsFailed always has a run; LevelFailed can have no run or retain the old run after a failed definition load. That old run still ticks presentation, and its view status cannot recover LevelFailed.

After a definition arrives, the controller checks cancellation, releases the old run, stores the definition, and starts LevelRun. StartRun enters BindingViews. TickBinding, used for both BindingViews and ViewsFailed, calls TickView then selects Playing on Ready, ViewsFailed on Failed, or BindingViews while still binding. Thus changing a failed startup skin can clear failure, wait for its new view, and return to Playing without R. LevelFailed does not evaluate readiness.

StartRun constructs LevelRun and publishes it only after successful construction. LevelRun creates Simulation, then ViewLayer, and performs one initial presentation tick to request views. Constructor failure disposes acquired presentation before simulation and rethrows. StartRun logs the error once, leaves no run, and enters LevelFailed. Initial loading, R, and N share this failure boundary. LevelFailed + R reloads the attempted definition. In every other non-Loading state, including ViewsFailed, R rebuilds from the existing definition. ViewLayer includes root creation/parenting in its acquisition cleanup boundary. LevelRun disposal uses try/finally so simulation disposal still runs if view disposal throws; ReleaseRun clears its reference in finally. Cleanup exceptions otherwise propagate without aggregation.

Spawning supplies final positions explicitly, so placement does not depend on a zero-delta transform update. Cached successful prefabs allow warm restarts to create views immediately.

Every Tick snapshots and clears pending UI requests, dropping unavailable requests rather than carrying them into a replacement level. A non-Loading Tick calls HandleSkinInput, then TickState(deltaTime, undoRequested), then HandleCommands only when the explicit TickResult is ProcessCommands and the state is not Loading. TickResult.SkipCommands ends R/N processing for the frame. TickState dispatches to TickBinding, TickPlaying, TickCompleted, or TickLevelFailed. TickPlaying accepts an eligible undo before submitting forward input, then ticks Simulation (undo -> validation -> application -> move count -> goal tracking -> win check -> countdown) then ViewLayer (skin switch -> binding -> actor motion -> projection -> player animation -> box goal feedback). An unsolved timeout immediately restarts the same definition with a fresh budget and the selected skin, using normal run disposal and startup binding. TickState returns SkipCommands after this restart, preventing another R/N action in that frame. Otherwise it checks view failure before completion, so view failure takes priority over a win in the same tick. Core completion remains latched and can enter Completed after view recovery. TickCompleted ticks presentation and advances the separate completion-delay timer; at the configured delay (default 0.75 seconds) it loads the next level if one exists, otherwise enters Finished while retaining the last run. TickState returns SkipCommands after this automatic progression, preventing a second command even if loading completes synchronously. Only the development N shortcut wraps; Finished ignores N and movement, continues presentation and K skin changes, and uses R to clear results and load index 0. HandleCommands gives N priority over R. Loading ignores controls. Definition-load exceptions enter LevelFailed. Run layers dispose in reverse: view cancellation/root/pipeline/queries first, simulation systems/world second. Controller disposal cancels its own text loading and releases its run; it never disposes the shared provider.

Only Playing ticks Simulation, using the elapsed gameplay delta. BindingViews, ViewsFailed, LevelFailed, Completed, and Finished call LevelRun.TickView, leaving all Core work untouched; Loading skips both layers. Pending skin rebinds during Playing therefore consume time, while startup binding and view-failure recovery pause the countdown. Every new run starts at the configured limit, including R, timeout restart, and automatic/manual level changes. GameplayController uses Unity's scaled Time.deltaTime; no timer UI is installed yet.

IGameplayStatus exposes Phase, 1-based LevelNumber, LevelCount, RemainingSeconds, Moves, and a read-only view of completed LevelResult values. Results are completion history in recording order; restarting, timing out, or using N does not append a result. Only R in Finished clears that history. LevelCount is zero until config loading supplies the level source count. Moves is zero without a run; RemainingSeconds retains its existing config-read contract when no run exists. GameplayDebugOverlay is an optional scene-attached IMGUI placeholder injected through IGameplayStatus. It shows unknown count/time before configs are available, then phase, level, time, moves, and in Finished each recorded result, totals, and the replay instruction. It is supplied as code and must be attached to the saved gameplay scene manually.
ServicesInstaller retains its serialized LevelRoot reference/alias and no HintArrow prefab reference. It binds HintSolver, IHintService/HintService, and HintCoordinator as singletons; HintCoordinator is bound as self only and owned by GameplayController. It binds IAddressablesService to one stateless AddressablesService and IStaticDataProvider to one shared StaticDataProvider, plus ILevelSource, IPlayerInput, LevelRoot, and ViewAssets. IStaticDataProvider includes IDisposable so GameplayLifetime can own provider cleanup through the interface; the provider is not separately registered as IDisposable. It does not bind individual config assets. GameplayInstaller binds GameplayLifetime as the sole automatic disposal owner for GameplayController, ViewAssets, and StaticDataProvider. Their own IDisposable contracts remain available for explicit ownership, but are excluded from Zenject registration to prevent duplicate disposal. GameplayLifetime releases the controller first, cached views second, and static configs last, keeping assets alive until their consumers finish cleanup. Nested try/finally blocks attempt every stage; cleanup exceptions propagate without aggregation or idempotence flags. No numeric disposal priorities are needed. ServicesInstaller binds LevelPopulator, SimulationPipelineFactory, ViewPipelineFactory, and LevelRunFactory as concrete singletons. LevelRunFactory receives root, provider, populator, and both pipeline factories, and creates each LevelRun with its LevelDefinition and readonly RunOptions (Skin, TimeLimitSeconds, and MoveDurationSeconds). LevelRun forwards the populator and Core factory into Simulation and the presentation factory into ViewLayer. Pure C# tests construct and pass the populator and Core factory directly. Each factory Create call acquires fresh systems; sharing factories never shares pipelines or run state. Factories neither tick nor dispose completed pipelines, and no FeaturesInstaller is needed. The provider loads the three GameplaySettings, LevelList, and ViewCatalog assets from the string label Configs. GameplayInstaller binds the controller as self, IInitializable, ITickable, IGameplayStatus, and IGameplayCommands, plus GameplayLifetime as self and IDisposable. GameplayController receives IPlayerInput, ILevelSource, LevelRunFactory, IStaticDataProvider, and HintCoordinator through an internal constructor marked Inject; Sokoban.Unity grants Sokoban.PlayModeTests friend access for direct fixture construction. GameplaySettings is a ScriptableObject whose authored LevelTimeLimitSeconds must be finite and positive (default 60), CompletionDelaySeconds finite and nonnegative (default 0.75), and MoveDurationSeconds finite and positive (default 0.16). The config itself performs no validation. RunOptions has no movement-duration default; its production and test call sites pass the settings value explicitly. ActorMotionSystem trusts the configured duration. There is no raw float binding. A future per-level override belongs in LevelList entries with fallback to this default; no override is implemented. No World, run, or pipeline is globally bound.

KeyboardMoveInput requires a connected keyboard, per the approved input contract. Movement, R, and Editor/development N access Keyboard.current directly; there is no missing-keyboard fallback. Ordinary-player N still returns false without accessing the device.

Sokoban.Editor.Tests also hosts public-API EditMode actor-motion/projection tests. It references Sokoban.Core and Sokoban.Unity, with explicit DefaultEcs.dll and nunit.framework.dll references. No new asmdef or friend assembly was introduced.

## Core organization, goal messages, and debug commands

Core remains one Unity-independent Sokoban.Core assembly. Runtime contains Simulation and SystemPipeline; Level contains parsing, definitions, population, and LevelResult; Ecs contains components and systems; Messages contains domain notifications. Namespaces and existing assembly friendships are preserved. The three pure Core test assemblies remain separate; consolidation is deferred.

Each populated box starts with BoxGoalState holding its initial position. GoalTrackingSystem runs after movement and move counting, compares the current box position with that snapshot, updates the snapshot, and publishes one readonly BoxEnteredGoal(Box, Goal) message when a changed position matches a goal. Initial boxes on goals do not publish; stationary ticks and blocked pushes do not publish; adjacent-goal movement and leaving/re-entering each publish new arrivals. The notification observes a fully committed move but precedes win and timer processing. Subscribers must not re-enter or mutate Core from the synchronous callback.

BoxGoalFeedbackComponent contains only a BoxGoalAnimator facade reference. BoxGoalFeedbackState contains only the notified goal position while feedback is owned by ECS. BoxGoalFeedbackSystem owns the World.Subscribe<BoxEnteredGoal> subscription and buffers notifications in its synchronous callback. Its presentation update coalesces arrivals per entity, rejects stale/foreign/dead arrivals, waits for ViewMove and ViewPending to clear and a bound view to exist, then calls PlayGoalFeedback() on the facade. It contains no animation formulas, baseline transforms, or tween handles.

BoxGoalFeedbackCompositeSystem is an ISystem<float> composite, distinct from the BoxGoalFeedbackSystem message reaction system. Its owned SequentialSystem runs BoxGoalFeedbackLifecycleSystem before BoxGoalFeedbackSystem and gates both through the composite's IsEnabled property. Construction releases acquired children if a later child fails. The lifecycle system stops feedback on new movement or leaving the notified goal, advances existing facade playback using the presentation delta, and removes completed goal tracking. Reverse disposal first unsubscribes/clears pending messages, then stops active facades before releasing the lifecycle query. Adapter uninstall also calls StopAndRestore immediately and removes both feedback components; adapter/facade disable and destruction provide view-owned cleanup without another ECS tick. Stop/restore is repeatable.

BoxGoalAnimator owns the authored Visual-child local position and scale plus one PrimeTween Sequence. It uses explicit local-position and scale tweens for a small hop and squash/stretch, and exact pose restoration on normal completion or interruption. Its only completion callback restores its own Unity transforms; the facade and callbacks never reference ECS entities or worlds. Grid projection retains ownership of the root. The facade exposes PlayGoalFeedback, Tick, StopAndRestore, and IsPlaying.

The sequence uses scaled-time settings and is kept paused in PrimeTween's automatic Unity update loop. The lifecycle system calls facade Tick with the existing scaled presentation delta; the facade advances the supported public Sequence.elapsedTime timeline and calls Complete at its endpoint. This deliberately avoids a global PrimeTween manual-update service, manager changes, or experimental defines. Skipping ViewLayer ticks (for example during controller Loading) freezes feedback even while Unity frames continue; zero scaled delta also freezes it. Completed/Finished and view-failure presentation retain their existing TickView behavior. Cosmetic completion never delays level progression.

BoxGoalAnimator authors its own serialized durationSeconds (0.22), height (0.12), and squashAmount (0.12) on the saved box prefab. PlayGoalFeedback() takes no arguments; the reaction system requests playback without carrying visual tuning. GameplaySettings, GameplayController, RunOptions, ViewContext, and the feedback feature contain no feedback options.
