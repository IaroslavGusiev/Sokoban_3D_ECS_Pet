# Sokoban architecture

Current design, checked against source on 2026-10-25. This document describes implemented behavior and ownership. Start with [setup](SETUP.md) to run or author content. Completed milestones and their test results are [historical records](history/README.md), not current setup instructions.

## Purpose and boundaries

This pet project exercises deterministic DefaultEcs rules and explicit OOP ownership around asynchronous Unity presentation. Gameplay includes moves, pushing, walls, win detection, a level countdown with automatic restart on timeout, automatic level progression, R restart, K player-skin cycling, and temporary N level cycling in Editor/development builds. Skin selection and all skin components live in presentation; switching skins does not mutate gameplay state.

| Folder under Sokoban/Assets/_Sokoban/Code | Assembly | Namespace | Responsibility |
| --- | --- | --- | --- |
| Core | Sokoban.Core | Sokoban.Core | Commands/components, parsing/population, movement, Simulation and Core pipeline. |
| Unity | Sokoban.Unity | Sokoban.Presentation | Composition, input/controller, text loading, shared prefab cache, per-run binding and projection. |
| Editor | Sokoban.Editor | Sokoban.Editor | Addressable string-address validation; excluded from players. |

Unity is 6000.0.63f1, DefaultEcs 0.17.2, Zenject 9.2.0, Addressables 4.1.1, and UniTask 2.5.11 from the existing Assets/Plugins installation. PrimeTween 1.5.1 is already installed from Packages/com.kyrylokuzyk.primetween.tgz through the existing local-tarball UPM entry; this refactor reuses that dependency. Core has noEngineReferences/overrideReferences enabled; its compiled references remain netstandard and DefaultEcs only.

Editor address validation and its tests live in the Editor-only Sokoban.Editor and Sokoban.Editor.Tests assemblies. [ASSEMBLIES.md](ASSEMBLIES.md) inventories all 22 source/vendored asmdefs and the resolved-package snapshot. Core friends only Sokoban.EditModeTests (internal movement systems) and Sokoban.App.EditModeTests (internal Simulation constructor/MovementFeature). The unused Sokoban.PlayModeTests entry was removed. Sokoban.Core.Tests uses public Core APIs, has no Unity references, and its source namespace is Sokoban.CoreTests.

## Deterministic Core

GridPosition is an immutable integer X/Y value. PlayerTag, BoxTag, WallTag, GoalTag, and FloorTag are readonly structs. Simulation.Send accepts cardinal MoveCommand values and preserves the first pending MoveRequest.

Simulation owns a new World and a SystemPipeline composed from the ordered RuleFeatures list: MovementFeature (validation then application), MoveCountFeature, GoalTrackingFeature, WinFeature, then LevelTimerFeature. WinCheckSystem iterates goal and box entity sets directly without per-tick collections or LINQ, and sets LevelCompletedTag on the dedicated level-state entity once every goal is occupied by a box. Simulation.IsCompleted exposes that tag. Completion is latched; Simulation.Send rejects commands after completion or timeout. Construction failures release acquired resources before propagating; normal disposal releases systems before the world. Cleanup exceptions propagate, without aggregation or idempotence flags.

Simulation retains explicit private _player and _levelState references in its owned World. After LevelPopulator creates the board and player, Simulation creates exactly one nonvisual entity with LevelStateTag, LevelTimer, and MoveCount. This entity has no GridPosition, view-kind tag, or presentation adapter; the existing view query excludes it. PlayerTag, GridPosition, movement requests/plans, and player-specific presentation components remain on the player. Both entities end with the Simulation world. LevelTimer carries RemainingSeconds on the level entity. Authored durations are finite and positive, and every attempt starts with the supplied budget. LevelTimerSystem queries LevelStateTag/LevelTimer entities without LevelCompletedTag or LevelTimedOutTag. It returns without writing on zero delta; otherwise it subtracts the supplied delta, clamps at zero, removes pending MoveRequest/MovementPlan from its captured player at expiration, and adds LevelTimedOutTag. Win runs first, so a winning move on the final tick succeeds and leaves the timer at its value before that tick. The timer then stays frozen through query exclusion. Simulation.Tick forwards the supplied delta without validation and always ticks its pipeline; terminal rules live in Core systems and Send. Simulation reads IsCompleted, IsTimedOut, RemainingSeconds, and Result from _levelState and sends movement requests only to _player; LevelRun forwards Result and the controller exposes status through IGameplayStatus. Time is synchronous input to Core; no Unity clock, async delay, or wall clock enters the rules.

The level entity holds readonly MoveCount with only Value. MoveCountSystem captures the single tagged player and its starting GridPosition during construction, retaining the previous-position snapshot privately for that run. It queries LevelStateTag/MoveCount, runs directly after movement, compares the player position with the private snapshot, and increments the level count at most once per tick. Blocked moves and pushes leave it unchanged; the count includes the winning move before WinCheckSystem latches completion. Simulation.Result is a readonly LevelResult with Moves, ElapsedSeconds, and RemainingSeconds. ElapsedSeconds is the original time limit minus the current timer, so completion preserves the existing freeze-before-winning-tick-decrement behavior. No movement validation or application rule was changed.
LevelPopulator is a public, sealed, stateless Core instance. Its Populate(World, LevelDefinition) method creates the player, walls, and boxes as separate entities. It also creates exactly Width * Height floor entities covering every cell, including cells underneath walls. Each floor has GridPosition and FloorTag; goal positions additionally have GoalTag on that same floor entity. There are no separate goal entities. LevelPopulator still creates 76, 78, and 98 board entities/views for the three shipped levels. Simulation adds one nonvisual level-state entity, making total Core counts 77, 79, and 99; expected view counts remain 76, 78, and 98. Simulation requires the populator through its constructor and still creates, owns, and disposes its world; the populator retains no world or run state and has no Zenject dependency.

MovementValidationSystem consumes requests, rejects blocked/invalid moves, and creates a MovementPlan. The earlier integer-overflow, multiple-player, and abandoned-plan guarantees remain unresolved contract mismatches described under Verification and limits; this level-state refactor leaves validation/application rules unchanged. A push stores box then player steps with expected source positions. ApplyMovementSystem preflights every participant, consumes the plan, and writes positions through entity.Set. Destroyed, disabled, moved, foreign-world, or missing participants reject the plan before writes.

DefaultEcs notifications are synchronous: an observer can see the box position change before the player's change. Observers must not mutate participants, re-enter movement, or throw during commit; there is no rollback for arbitrary observer exceptions. Runtime movement has no explicit board-bounds check; text parsing validates playable-area enclosure.

SystemPipeline creates features in explicit list order. It owns a SequentialSystem, which checks its own IsEnabled and disposes children in reverse. Child rule systems retain their interface properties without local enable guards. Individual child-system disabling is unsupported.

## Parsing and tests

LevelParser accepts #, -, @, $, ., *, and +. Text starts at the highest y coordinate; Up is +y. CRLF is normalized, trailing empty rows ignored, and row characters preserved. Diagnostics identify invalid symbols/rows and begin with line N: or level:. Validation checks rectangular rows, one player, at least one box, equal box/goal counts, and a four-direction flood fill enclosed by walls. Boxes/goals are passable for enclosure; unreachable edge cells, including diagonal-only adjacency, are valid.

After checking box/goal counts, LevelParser rejects an already solved level with "level: the level is already solved; leave at least one box off its goal." The three shipped levels still parse and solve. LevelDefinition validates positive dimensions and nonnull collections at its public boundary. No Unity or async types enter the model.

Core.Tests discovers every Assets/Levels/*.txt. The independent BFS LevelSolver returns the shortest move sequence plus the player's predicted GridPosition after each move, with a 2,000,000-state cap. Replay sends each move through a real Simulation and asserts each player position and final box/goal positions. The shipped solutions remain 6, 12, and 11 moves. Solver code is test-only.

## Ownership

| Owner | Resources |
| --- | --- |
| StaticDataProvider | One Addressables batch handle for the Configs label, retained across level runs and released after consumers on scene disposal. |
| AddressableLevelSource.LoadAsync | One temporary text handle, released in finally after parsing/failure/cancellation. |
| ViewAssets | One cached prefab handle per resolved ViewKey. Fallback requests share the Default handle. Same-frame failures are shared; failed entries are released and evicted on a request in a later frame. |
| GameplayController | Controller cancellation source, current LevelDefinition/index, completion timer, chosen player SkinId, and one private LevelRun. |
| LevelRun | Simulation, ViewLayer, and one buffered movement command; construction, initial binding tick, explicit tick order, and reverse disposal. |
| Simulation | World, explicit player and level-state entity references, and Core SystemPipeline. |
| ViewLayer | Per-run view root, cancellation source, ViewContext, presentation SystemPipeline, missing-view, failed-view, and player EntitySets. |
| GameplayLifetime | Scene shutdown: GameplayController, then ViewAssets, then StaticDataProvider, with nested finally blocks to attempt every cleanup if an earlier step throws. |
| Zenject | Service composition and automatic disposal of GameplayLifetime. |

ILevelSource exposes Count and UniTask<LevelDefinition> LoadAsync(index, token). AddressableLevelSource receives IStaticDataProvider and IAddressablesService and reads LevelCount and GetLevelConfig(index).Address after startup config loading. It awaits the Addressable TextAsset with explicit caller cancellation and auto-release disabled, parses it, and releases the handle in finally.

ViewCatalog groups skins by kind: each serializable KindEntry contains ViewKind and a List<SkinEntry>; each serializable SkinEntry contains SkinId and a string Address. Author exactly one group for every kind, unique skins within a group, a Default skin per group, and nonempty addresses. These are authoring requirements rather than config-level validation; Resolve uses Single for the kind and fallback entry. Resolve selects the kind group, then returns the exact SkinEntry or that group's Default. ViewAssets combines the requested kind with the returned skin to preserve resolved-key caching and passes Address directly to LoadAssetAsync<GameObject>. An existing but broken Alternate entry fails rather than falling back. LevelList stores ordered serializable LevelConfig entries containing Address strings, loaded as TextAsset by AddressableLevelSource. IStaticDataProvider.GetLevelConfig takes a zero-based index and returns the config entry; an invalid index fails loudly. See [setup](SETUP.md) for addresses and authoring, and [history](history/README.md) for the migrations.

Tools > Sokoban > Validate Addressable Addresses checks all saved ViewCatalog and LevelList assets against the Editor's Addressables settings: each configured address must match exactly one asset of the expected type in an included group, with address inclusion enabled for bundled groups. Editor APIs remain in Sokoban.Editor. Configs have no structural or blank-address validation. Missing/wrong-type built content follows the existing load failure and recovery paths. Editor validation does not prove that an existing content build is current; rebuild Addressables after changing content or addresses.

ViewAssets implements IViewProvider and IDisposable. IViewProvider.LoadAsync takes ViewKey and CancellationToken. ViewKey is an immutable equatable Kind/Skin pair; SkinId contains Default (Doctor), Alternate (Farmer), and Punk. The provider resolves the catalog entry first and keys its cache by that entry's pair, so absent alternate skins reuse the same Default handle. Its constructor retains IStaticDataProvider without loading anything; LoadAsync reads the loaded ViewCatalog through GetViewCatalog. Cache misses start one IAddressablesService.Load<GameObject>; concurrent callers for the same resolved pair reuse the pending/successful handle. Each caller uses IAddressablesService.AwaitAsync with its cancellation token; the service observes cancellation immediately and never automatically releases the shared handle. Cancellation stops the caller's wait; the shared handle remains owned by the provider. Cancelling a caller never cancels or releases the shared handle. Successful prefabs stay cached across K, R, and N. CachedLoad.OnCompleted records Time.frameCount on failure, including immediate failure at creation. Requests in that frame share the failed handle and exception. A request in a later frame removes the failed cache entry and releases its still-valid handle before starting a fresh load. This prevents synchronous invalid-key failures from creating one failed handle/log per entity in a binding tick.

Failures log once per load attempt, covering synchronous catalogue/setup/conversion failures and asynchronous operation failure. A CachedLoad entry deduplicates its completion-callback log and its callers' exception-path logs, even if all callers stopped waiting. Cancellation is propagated without an error log. Each affected entity is separately marked ViewFailed; the binding operation does not duplicate provider logs. A later request can retry and can produce a new failure log. Current entities with ViewFailed do not retry automatically; a skin request clears their failure marker, while R or N builds a fresh run. A stale request's result or failure cannot bind or mark failure for a different desired ViewKey. Exceptions from instantiation/adapter installation remain logged by their binding operation.

Release while loading uses immediate owner release, without awaiting underlying completion. Addressables' internal execution reference survives until completion and final destruction. Addressables 4.1.1 also invalidates outstanding handles during ExitingPlayMode, potentially before Zenject's OnDestroy disposal. The approved IsValid checks remain at provider disposal and temporary text cleanup to skip already-invalidated handles.

## ECS presentation flow

### Addressables access

IAddressablesService exposes typed Load(address), LoadByLabel(label), AwaitAsync(handle, token), and Release(handle). ServicesInstaller binds one stateless AddressablesService. It is the only runtime class that calls Addressables loading/release APIs or converts handles to UniTask. It adds no cache and owns no handles. AddressableLevelSource, StaticDataProvider, and ViewAssets receive it through constructor injection and retain their respective temporary, scene-config, and prefab-cache ownership policies.

AwaitAsync observes cancellation immediately and disables automatic handle release. Cancelling one waiter does not release an asset or cancel the underlying shared operation; the owner still releases its acquired reference exactly once. Release checks handle validity to tolerate Addressables invalidation on Play Mode exit. It does not make releasing the same live reference twice safe, because another owner can keep the shared operation valid. Config retry/validation, view failure logging and retry, and level parsing remain with their current owners.

### Static config loading

The assets in Assets/Addressables/Config are GameplaySettings.asset, LevelList.asset, and LevelViewCatalog.asset. Their stored settings use field-targeted SerializeField auto-properties with public getters and private setters. GameplaySettings exposes timer, completion-delay, and movement float properties; LevelList.Levels is a serialized array; ViewCatalog.Entries and KindEntry.Skins are lists. Config classes contain no Validate methods or FormerlySerializedAs attributes. Values are authored and saved through the Unity Editor using the current serialized backing-field names; existing values were saved through Editor APIs before removing migration support. They retain their GUIDs after moving out of Resources. StaticDataProvider.LoadAsync uses IAddressablesService.LoadByLabel<ScriptableObject> and AwaitAsync to load the Configs label, requires exactly one of each expected type, and publishes the resulting config set. All three configs are trusted authored data without runtime Validate calls. GetGameplaySettings, GetViewCatalog, GetLevelConfig(index), and LevelCount are synchronous reads after loading. A read before readiness fails loudly; there is no Resources fallback or default config creation. Consumers retain the provider during construction and access configs during the owned startup/load flow. GameplayController.RemainingSeconds requires completed config loading when no run exists.

Pending callers share one preserved initialization task. The caller starting that attempt controls its cancellation; a later waiter's cancellation only ends its own wait. Provider disposal also cancels the attempt. Failed, missing/duplicate-type, or cancelled attempts release their owned batch and clear it for retry. Completed configs stay cached for the scene lifetime. A captured attempt identity prevents cancellation/disposal cleanup from releasing another attempt, and a token check after awaiting prevents late completion from publishing cancelled data. Addressables handle IsValid checks cover Editor play-mode invalidation. Config handles remain separate from ViewAssets prefab handles and AddressableLevelSource temporary text handles.

Editor address validation additionally requires one labeled asset per config type and checks group/catalog label inclusion. The runtime label load requires the expected config types in actual built content; changing saved assets or label assignments still requires rebuilding Addressables for Use Existing Build.

### Entity and view lifetime contract

Within a run, existing entity identities, kind-selection tags, and GridPosition component presence remain stable. Movement changes GridPosition values through entity.Set; binding reads the latest value after awaiting. Presentation-owned SkinChangeRequest/ViewSkin updates support replacing a bound view. Individual entity destruction/reuse, retagging, and external removal/replacement of a bound view remain unsupported within a run.

Presentation exclusively owns ViewPending, ViewFailed, ViewSkin, SkinChangeRequest, TransformComponent, and instantiated view GameObjects. Gameplay and external callers must not remove these components or destroy the views independently; request player skin changes through the owned application/view-layer API. Presentation failures may leave partial adapter writes until run disposal; Ready describes component presence, not ongoing Unity-object health. Tests that deliberately violate these conditions exercise query/failure mechanics, not a supported arbitrary dynamic-view API.

R/N replaces a whole run. ViewLayer cancels its binding token before Simulation disposes the world, so pending results cannot access entities from the old run. This run-level contract does not provide individual entity-generation validation. Dynamic entity/view ownership requires a separate design before it is supported.

### Binding and projection

Every visual now follows one path:

needs view -> ViewPending -> TransformComponent, or ViewFailed.

ViewKeyMap prioritizes WallTag, BoxTag, PlayerTag, GoalTag, FloorTag exactly as before, and reads the desired skin from ViewSkin, defaulting to Default when absent. Goal floors therefore select the Goal prefab.

ViewBindingSystem is a buffered AEntitySetSystem<float>. ViewQuery.Viewable defines the common filter once: GridPosition and one of those tags using DefaultEcs 0.17.2 WithEither/Or. Binding adds exclusions for ViewPending, ViewFailed, and TransformComponent. It sets ViewPending first, then starts its owned async bind. No per-entity pending dictionary or retained task list exists outside ECS components.

Each bind captures the requested ViewKey. After awaiting IViewProvider with the run token, the bind checks cancellation before touching the entity, then recomputes ViewKeyMap.Get(entity). A different key drops the result and removes ViewPending, allowing a new request next tick without instantiating a stale view. Both provider and instantiation/adapter failures call Fail(entity, requestedKey): cancelled runs return before ECS access, stale requests only remove ViewPending, and current requests set ViewFailed and remove ViewPending. The existing active-run instantiation-exception log remains. For a current success, binding reads the latest GridPosition, instantiates under ViewContext.Root at the current grid or interpolated position, restores player facing (other views keep prefab rotation), and names the instance Key (x, y). ViewKey.ToString preserves Kind for Default and prints Kind/Alternate for Alternate. If the prefab root has EntityView, its adapters install first. During an existing ViewMove, binding uses its current interpolated position; player facing is restored from ActorViewState. The binder then uses entity.Set(new TransformComponent(view.transform)) and removes ViewPending.

EntityView and the adapter hierarchy stay. EntityAdapter declares Install and Uninstall; ComponentAdapter<T> installs its serialized struct through Set and uninstalls through Remove<T>. TransformAdapter and PlayerAnimatorAdapter are the concrete production adapters and inherit both methods. Its initial write is redundant but harmless because the binder sets the authoritative view transform afterward. EntityView forwards both operations to its adapters. Uninstall is invoked only by SkinSwitchSystem, never from OnDisable/OnDestroy. EntityView is optional, and ordinary prefabs can bind without it.

FeaturesInstaller binds one ViewFeatures instance. LevelRunFactory passes that instance through LevelRun to ViewLayer, which calls its instance Create method. The presentation feature list is SkinSwitchFeature, ViewBindingFeature, ActorMotionFeature, TransformSyncFeature, PlayerAnimationFeature, then BoxGoalFeedbackFeature. The buffered SkinSwitchSystem consumes SkinChangeRequest, uninstalls adapters from an existing EntityView, destroys the old GameObject, removes TransformComponent, writes ViewSkin, clears ViewFailed, and consumes the request. Existing ViewPending remains until its awaited operation completes or the run is cancelled. GridTransformSyncSystem projects every bound entity into Unity world space (X, 0, Y), including floor cells. Destroyed Unity transforms are skipped using Unity null semantics. Projection never writes gameplay positions back. Player and box views interpolate during ViewMove; other views project immediately. Player rotation follows its last successful move.

ViewLayer creates its own root, token source, context, pipeline, two readiness EntitySets, a player query, and a ViewMove query. The missing-view set uses ViewQuery.Viewable without TransformComponent; the failed-view set contains every entity with ViewFailed. Status is Failed if the failed set is nonempty, Binding if the missing set is nonempty, otherwise Ready. This includes unrequested viewable entities and gives failure priority even when a transform is present. No readiness system or stored aggregate ECS marker is needed.

ViewLayer owns a player query, writes the initial ViewSkin directly before the first tick, and SetPlayerSkin writes one SkinChangeRequest to every player. Dispose cancels before any world can be disposed, disables/destroys the root, disposes the pipeline and all four query sets, then disposes the token source. A late result returns without touching the old entity; Constructor failure releases acquired resources and rethrows.

## Player animation and visual movement

Core still commits complete moves and pushes synchronously. At the start of every Update, ActorMotionSystem initializes actors lacking ActorViewState through a dedicated EntitySet and reusable array buffer. It copies the set before component writes change membership, allocating only when buffer capacity must grow. New actors receive their current GridPosition, identity Facing, and HasFacing false. Each presentation tick compares these snapshots with current GridPosition values. A player entering the previous cell of a box that moved by the same delta is a successful push. Rejected requests do not change positions, start visual motion, or turn the player. No Unity reference or animation component was added to Core.

A changed actor receives ViewMove (From, To, Elapsed, Duration, IsPushing). Its elapsed time advances with the supplied presentation delta, and GridTransformSyncSystem interpolates the transform until the configured duration, then projects the exact destination after removing ViewMove. Player and box start in the same tick with the same duration. ActorViewState.HasFacing becomes true on the first detected movement. Until then, binding and projection preserve the prefab rotation. Afterward, ActorViewState preserves the player's facing across skin replacement. GridTransformSyncSystem writes position and rotation only when they differ from their targets. The view can retarget from its current interpolated position if an external caller changes simulation positions during motion; ordinary application input is buffered instead. A new run initializes without movement. Skin replacement keeps existing motion/facing and binds the new view at the current visual position. It does not restart the step or retain the previous Animator reference.

LevelRun retains at most one pending cardinal command; the first is preserved and further commands are dropped until it is submitted. On a Playing tick, it submits that command only when ViewLayer has no ViewMove, then ticks simulation and presentation. A step finishing in this tick permits submission on the next Playing tick. Core and the countdown continue ticking while input waits for visual movement. Commands cannot survive run replacement. Presentation motion still advances during view-failure recovery and completion; Loading skips it along with all presentation work.

Each Player_ZombieDoctor/Farmer/Punk prefab inherits PlayerBase, nests its corresponding model, and installs PlayerAnimatorComponent through PlayerAnimatorAdapter and EntityView. That presentation component references the PlayerAnimator MonoBehaviour facade, which wraps the nested Unity Animator. PlayerAnimationSystem queries the component and drives Moving plus the Push layer weight from ViewMove. Push weight blends over 0.05 seconds. Adapter uninstall removes the component before skin view destruction.

The three wrappers share AddressablesDependencies/Player/Animation/Player.controller, using imported Z_idle_A and the in-place Z_walk. Root motion is disabled on every wrapper. The Push layer uses an authored looping humanoid PushPose and an arm/finger Avatar Mask, leaving leg movement to the base layer. These are ordinary dependencies of the Addressable player prefabs. The addresses views/player, views/player_alt, and views/player_punk select Doctor, Farmer, and Punk respectively. Original model prefabs and the legacy cube player prefabs remain available; only the three wrappers are registered as player addresses.

## Controller and composition

GameplayController is the sole Zenject IInitializable/ITickable driver. Public Tick() delegates to internal Tick(deltaTime), which runs the full orchestration and supplies a deterministic seam for friend tests. GameplayLifetime owns its disposal along with ViewAssets and StaticDataProvider. The controller's only run field is a private LevelRun. LevelRun is internal, retains private Simulation/ViewLayer fields, forwards movement and completion/readiness queries, and ticks simulation before presentation. Simulation and ViewLayer each implement IDisposable directly. LevelRun calls their concrete Tick methods and owns their ordering; there is no shared layer interface or layer list.

The controller's _playerSkin survives restarts and level changes. Every new LevelRun receives it and forwards it to ViewLayer before initial binding. In a non-Loading tick with a run, HandleSkinInput uses SkinCycle.Next and sends SetPlayerSkin before layer ticking. SkinCycle caches Enum.GetValues and wraps over contiguous SkinId values 0..n-1, so adding a third enum value needs no controller change. KeyboardMoveInput maps this to K, with the existing required-keyboard contract. Readiness is re-evaluated in BindingViews and ViewsFailed. Playing ignores Binding status but transitions to ViewsFailed on Failed status after ticking the run. Subsequent simulation ticking and movement input pause while presentation keeps ticking; K can clear the failure and recover through BindingViews to Playing without R.

The controller keeps an enum-based state machine with Loading, BindingViews, Playing, Completed, ViewsFailed, LevelFailed, and Finished. All state changes go through TransitionTo(GameplayPhase next); entering Completed resets the completion-delay timer and appends the current run's LevelResult once. State handlers remain private controller methods. Initialize asynchronously loads the Configs batch, requires its expected config types, and then loads definition 0. Every definition-load attempt first awaits StaticDataProvider.LoadAsync, which returns immediately after a successful config load. R after config failure therefore retries the config stage before the attempted level. Loading returns before input, layer ticking, or command handling. In every other state an existing run ticks presentation; only Playing reads/sends movement input and ticks simulation. A queued Core request therefore remains pending while a replacement definition loads. The attempted index is stored before awaiting, so LevelFailed + R retries that index even if N failed before producing a definition. ViewsFailed always has a run; LevelFailed can have no run or retain the old run after a failed definition load. That old run still ticks presentation, and its view status cannot recover LevelFailed.

After a definition arrives, the controller checks cancellation, releases the old run, stores the definition, and starts LevelRun. StartRun enters BindingViews. TickBinding, used for both BindingViews and ViewsFailed, calls TickView then selects Playing on Ready, ViewsFailed on Failed, or BindingViews while still binding. Thus changing a failed startup skin can clear failure, wait for its new view, and return to Playing without R. LevelFailed does not evaluate readiness.

StartRun constructs LevelRun and publishes it only after successful construction. LevelRun creates Simulation, then ViewLayer, and performs one initial presentation tick to request views. Constructor failure disposes acquired presentation before simulation and rethrows. StartRun logs the error once, leaves no run, and enters LevelFailed. Initial loading, R, and N share this failure boundary. LevelFailed + R reloads the attempted definition. In every other non-Loading state, including ViewsFailed, R rebuilds from the existing definition. ViewLayer includes root creation/parenting in its acquisition cleanup boundary. LevelRun disposal uses try/finally so simulation disposal still runs if view disposal throws; ReleaseRun clears its reference in finally. Cleanup exceptions otherwise propagate without aggregation.

Spawning supplies final positions explicitly, so placement does not depend on a zero-delta transform update. Cached successful prefabs allow warm restarts to create views immediately.

Every Tick snapshots and clears pending UI requests, dropping unavailable requests rather than carrying them into a replacement level. A non-Loading Tick calls HandleSkinInput, then TickState(deltaTime), then HandleCommands only when the explicit TickResult is ProcessCommands and the state is not Loading. TickResult.SkipCommands ends R/N processing for the frame. TickState dispatches to TickBinding, TickPlaying, TickCompleted, or TickLevelFailed. TickPlaying sends movement, ticks Simulation (validation -> application -> move count -> goal tracking -> win check -> countdown) then ViewLayer (skin switch -> binding -> actor motion -> projection -> player animation -> box goal feedback). An unsolved timeout immediately restarts the same definition with a fresh budget and the selected skin, using normal run disposal and startup binding. TickState returns SkipCommands after this restart, preventing another R/N action in that frame. Otherwise it checks view failure before completion, so view failure takes priority over a win in the same tick. Core completion remains latched and can enter Completed after view recovery. TickCompleted ticks presentation and advances the separate completion-delay timer; at the configured delay (default 0.75 seconds) it loads the next level if one exists, otherwise enters Finished while retaining the last run. TickState returns SkipCommands after this automatic progression, preventing a second command even if loading completes synchronously. Only the development N shortcut wraps; Finished ignores N and movement, continues presentation and K skin changes, and uses R to clear results and load index 0. HandleCommands gives N priority over R. Loading ignores controls. Definition-load exceptions enter LevelFailed. Run layers dispose in reverse: view cancellation/root/pipeline/queries first, simulation systems/world second. Controller disposal cancels its own text loading and releases its run; it never disposes the shared provider.

Only Playing ticks Simulation, using the elapsed gameplay delta. BindingViews, ViewsFailed, LevelFailed, Completed, and Finished call LevelRun.TickView, leaving all Core work untouched; Loading skips both layers. Pending skin rebinds during Playing therefore consume time, while startup binding and view-failure recovery pause the countdown. Every new run starts at the configured limit, including R, timeout restart, and automatic/manual level changes. GameplayController uses Unity's scaled Time.deltaTime; no timer UI is installed yet.

IGameplayStatus exposes Phase, 1-based LevelNumber, LevelCount, RemainingSeconds, Moves, and a read-only view of completed LevelResult values. Results are completion history in recording order; restarting, timing out, or using N does not append a result. Only R in Finished clears that history. LevelCount is zero until config loading supplies the level source count. Moves is zero without a run; RemainingSeconds retains its existing config-read contract when no run exists. GameplayDebugOverlay is an optional scene-attached IMGUI placeholder injected through IGameplayStatus. It shows unknown count/time before configs are available, then phase, level, time, moves, and in Finished each recorded result, totals, and the replay instruction. It is supplied as code and must be attached to the saved gameplay scene manually.
ServicesInstaller retains only its serialized LevelRoot reference and alias. It binds IAddressablesService to one stateless AddressablesService and IStaticDataProvider to one shared StaticDataProvider, plus ILevelSource, IPlayerInput, LevelRoot, and ViewAssets. IStaticDataProvider includes IDisposable so GameplayLifetime can own provider cleanup through the interface; the provider is not separately registered as IDisposable. It does not bind individual config assets. GameplayInstaller binds GameplayLifetime as the sole automatic disposal owner for GameplayController, ViewAssets, and StaticDataProvider. Their own IDisposable contracts remain available for explicit ownership, but are excluded from Zenject registration to prevent duplicate disposal. GameplayLifetime releases the controller first, cached views second, and static configs last, keeping assets alive until their consumers finish cleanup. Nested try/finally blocks attempt every stage; cleanup exceptions propagate without aggregation or idempotence flags. No numeric disposal priorities are needed. ServicesInstaller binds LevelPopulator and LevelRunFactory as shared concrete instances. The factory receives root, provider, ViewFeatures, and populator, and creates each LevelRun with its LevelDefinition and readonly RunOptions (Skin, TimeLimitSeconds, and MoveDurationSeconds). LevelRun forwards the populator into Simulation. Pure C# tests construct and pass the populator directly. FeaturesInstaller binds ViewFeatures. The provider loads the three GameplaySettings, LevelList, and ViewCatalog assets from the string label Configs. GameplayInstaller binds the controller as self, IInitializable, ITickable, IGameplayStatus, and IGameplayCommands, plus GameplayLifetime as self and IDisposable. ## Core organization, goal messages, and debug commands

The prefab-tuning cleanup on 2026-10-25 passed all 16 BoxGoalFeedbackTests (including custom serialized tuning and the saved prefab), all 13 HardcodedLevelTests, and all three ConfigSerializationTests. Addressable address validation and the content rebuild also passed. Core behavior and tests were unchanged; the full EditMode suite was not rerun, and its previously recorded 21 failures remain outside this cleanup.

Core remains one Unity-independent Sokoban.Core assembly. Runtime contains Simulation and SystemPipeline; Level contains parsing, definitions, population, and LevelResult; Ecs contains components and systems; Features contains IFeature, RuleFeatures, and feature composition; Messages contains domain notifications. Namespaces and existing assembly friendships are preserved. The three pure Core test assemblies remain separate; consolidation is deferred.

Each populated box starts with BoxGoalState holding its initial position. GoalTrackingSystem runs after movement and move counting, compares the current box position with that snapshot, updates the snapshot, and publishes one readonly BoxEnteredGoal(Box, Goal) message when a changed position matches a goal. Initial boxes on goals do not publish; stationary ticks and blocked pushes do not publish; adjacent-goal movement and leaving/re-entering each publish new arrivals. The notification observes a fully committed move but precedes win and timer processing. Subscribers must not re-enter or mutate Core from the synchronous callback.

BoxGoalFeedbackComponent contains only a BoxGoalAnimator facade reference. BoxGoalFeedbackState contains only the notified goal position while feedback is owned by ECS. BoxGoalFeedbackSystem owns the World.Subscribe<BoxEnteredGoal> subscription and buffers notifications in its synchronous callback. Its presentation update coalesces arrivals per entity, rejects stale/foreign/dead arrivals, waits for ViewMove and ViewPending to clear and a bound view to exist, then calls PlayGoalFeedback() on the facade. It contains no animation formulas, baseline transforms, or tween handles.

BoxGoalFeedbackFeature composes BoxGoalFeedbackLifecycleSystem before the message reaction system. The lifecycle system stops feedback on new movement or leaving the notified goal, advances existing facade playback using the presentation delta, and removes completed goal tracking. Reverse disposal first unsubscribes/clears pending messages, then stops active facades before releasing the lifecycle query. Adapter uninstall also calls StopAndRestore immediately and removes both feedback components; adapter/facade disable and destruction provide view-owned cleanup without another ECS tick. Stop/restore is repeatable.

BoxGoalAnimator owns the authored Visual-child local position and scale plus one PrimeTween Sequence. It uses explicit local-position and scale tweens for a small hop and squash/stretch, and exact pose restoration on normal completion or interruption. Its only completion callback restores its own Unity transforms; the facade and callbacks never reference ECS entities or worlds. Grid projection retains ownership of the root. The facade exposes PlayGoalFeedback, Tick, StopAndRestore, and IsPlaying.

The sequence uses scaled-time settings and is kept paused in PrimeTween's automatic Unity update loop. The lifecycle system calls facade Tick with the existing scaled presentation delta; the facade advances the supported public Sequence.elapsedTime timeline and calls Complete at its endpoint. This deliberately avoids a global PrimeTween manual-update service, manager changes, or experimental defines. Skipping ViewLayer ticks (for example during controller Loading) freezes feedback even while Unity frames continue; zero scaled delta also freezes it. Completed/Finished and view-failure presentation retain their existing TickView behavior. Cosmetic completion never delays level progression.

BoxGoalAnimator authors its own serialized durationSeconds (0.22), height (0.12), and squashAmount (0.12) on the saved box prefab. PlayGoalFeedback() takes no arguments; the reaction system requests playback without carrying visual tuning. GameplaySettings, GameplayController, RunOptions, ViewContext, and the feedback feature contain no feedback options. The facade uses the existing PrimeTween 1.5.1 package, and owns playback and exact baseline restoration. Existing prefab tuning and GUIDs are preserved.

IGameplayCommands exposes CanRestart, CanSwitchSkin, RequestRestart, and RequestNextSkin. Requests coalesce with the corresponding keyboard input and are consumed once by the normal controller tick. Loading rejects both actions; skin switching additionally requires an existing run. Automatic progression and timeout restart retain their same-frame command suppression. The IMGUI overlay keeps status/results on the left and places Restart / Switch skin buttons at the top right, using its configured font size. In Finished, Restart reads Play again and uses the existing replay/reset behavior. OnGUI queues requests and never directly replaces a run. GameplayLifetime remains the sole automatic disposal owner.

Test ownership scenarios now instantiate the real StaticDataProvider with controlled Addressables operations. ViewAssets tests observe injected load/release calls rather than constructing private cache entries, and controller phase scenarios use full deterministic ticks instead of assigning Phase or invoking private TickState. A nondefault movement-duration integration test covers settings-to-ViewLayer propagation. Redundant pending-handle-release and LevelList serialization tests were removed from PresentationPipelineTests; service/Editor coverage remains.
