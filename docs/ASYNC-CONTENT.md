## Ownership and release approach

AddressableLevelSource loads a TextAsset, parses it, and releases its temporary handle in finally before starting any prefab load. A parser error therefore fails before prefab loading. ViewAssets starts the prefab loads in parallel, records each started handle before building the lookup, and awaits UniTask.WhenAll. Its factory catch releases every started handle on failure/cancellation; after success the returned ViewAssets owns those handles. LevelContent owns ViewAssets and exposes IViewAssets to its consumers.

Every cancellable Addressables await explicitly uses `autoReleaseWhenCanceled: false`; only the owner releases the handle. `cancelImmediately: true` stops waiting promptly when the lifetime token is cancelled. The underlying load continues independently.

All three release boundaries check handle.IsValid() before releasing: the text handle's finally block, ViewAssets.LoadAsync failure/cancellation cleanup, and ViewAssets.Dispose. This handles Addressables 4.1.1 invalidating outstanding handles during ExitingPlayMode before Zenject's OnDestroy disposal. It preserves normal ownership and continues releasing any still-valid handles.

The installed Addressables 4.1.1 documentation (`load-wait-asynchronous-coroutines.md`) explicitly permits releasing an unfinished load. Its AsyncOperationBase.Start retains an internal reference until completion. We therefore release our handle immediately on failure/cancellation, including unfinished operations; we do not await completion just to release it. A focused test starts an unfinished ResourceManager operation, releases its external handle, completes it, and verifies destruction happens exactly once at completion.

GameplayController owns the lifetime CancellationTokenSource, loaded LevelContent, private Simulation, and ordered run layers. Initialize starts index 0 through Forget, whose async method contains the single error boundary. While Loading, Tick does nothing and any old run remains visible and frozen. A successful load first releases the old run, then old content, adopts the new content, and starts the new run. New prefab references are acquired before old references are released so shared assets remain cached.

R releases/recreates only the run, with no await or reload. **N is a temporary developer next-level shortcut**, wrapping `(index + 1) % Count`; it is not win detection. Both are handled after the current layer loop. Disposal cancels the lifetime, releases the run, and disposes content if present. A late result after cancellation is disposed without constructing/ticking a simulation. Unadopted results have one local cleanup owner until ownership transfers to the content field. Cancellation is ignored at the boundary; other errors are logged once by the controller and leave it out of Playing. No automatic retry or loading UI was added.

## Manual verification checklist

- Enter Play Mode: the first level loads, then arrows/WASD move and push boxes with the same wall rules.
- Press R repeatedly: the board resets immediately and no new text/prefab loads start. The loaded content stays owned across restarts.
- Press N: the three levels cycle and wrap. During a pending load the old level stays visible and frozen; the new board replaces it only after its content is ready.
- Inspect handle counts during switches: the old content's references are released after replacement content is acquired. Shared prefabs can remain referenced/cached by the new content. Leaving Play Mode releases the current content; a cancelled pending load releases its started handles, although its underlying work may finish later.
- Deliberately break a reference, then restore it. An invalid authoring reference fails composition validation. For the async failure path, use a syntactically valid reference whose Addressable content cannot resolve/load. With Log Runtime Exceptions disabled as above, the controller logs one exception, stays out of Playing, and releases the failed attempt's handles; a previously loaded board remains frozen and owned until teardown. Fix the reference and restart Play Mode; no retry behavior is added.
- Run **Window > General > Test Runner > EditMode**, all Sokoban assemblies. Then run **PlayMode > Sokoban.PlayModeTests**, including the saved-scene fixture after setup.

Select frames around a switch/disposal and inspect the **Handles** and **Status** columns.
